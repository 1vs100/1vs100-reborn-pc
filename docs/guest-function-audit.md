# Guest function audit: host replacement candidates

Scan of every file under `native/generated/` (312 files): 152 `.cpp` (150 `onevs100_recomp.N.cpp` units, `onevs100_init.cpp` with the 50,314-entry `PPCFuncMappings` table, `onevs100_register.cpp`), 153 headers (150 `onevs100_funcs.N.h`, `onevs100_funcs.h` with 49,641 declarations and 436 kernel imports, `onevs100_pch.h`, `onevs100_init.h`) and 7 build files. 49,878 `DEFINE_REX_FUNC` bodies were parsed for opcode mix, loops, constants and call edges. Names come from the 808-debug signature matches (`ida-1vs100-retail/signatures/808-to-1149-matches.json`, 6,414 names). The profile is `c174/profile10.log` (20 s, 4030 samples per thread) resolved with the matching build-347 map. `agg4` is the older aggregated profile.

Profile notation: `M` is the main thread (5) and `R` the render thread (6). Numbers are self samples out of 4030, with inclusive samples in brackets where they matter. `x` marks samples spent in a host DLL (ntdll, rexruntime) with that guest function as the first exe frame.

Where the time goes (profile10):

- Main thread: 69% (2771) is blocked in `WaitForMultipleObjectsEx` waiting for the render thread. 31% is guest code.
- Render thread: 38% (1522) is the host renderer (`draw::Capture`/`Build`, `StreamSnapshotPool::Copy`, `PlaceIndices`, allocations). 34% (1364) is guest code. 15% (614) is waiting in host `EndFrame` and 13% (524) is waiting for the main thread.
- The render thread is the critical path. Main-thread savings do not raise the frame rate until the render thread gets faster.

## D3D runtime work the native renderer could make redundant

The guest D3D runtime still runs in full. The draw hooks (`edge_draw.cpp`) call `cmdbuf::NotePending`, then the original `__imp__sub_822F3830` / `__imp__sub_822F3440`, then `draw::Capture`. The original body flushes the pending state into ring packets that nothing executes. On the render thread this costs about 200 samples (5%): ranks 2, 3, 8, 16, 17, 18, 21, 22, 23 and 24.

- **Skip the guest draw body when the draw is captured** (`sub_822F3830`, `sub_822F3440`, `sub_822F29A8` BeginVertices). Feasible. The renderer reads the device shadow (`ConstantSource`, `Guest<D3DDevice>`), runs its own vfetch patch on a scratch copy, and applies literal constants itself. What the guest body still provides:
  - It clears the pending bits at device+16 (`m_Pending`). If the bits are never cleared, later `SetPending_*` calls do the accumulated work at once.
  - It advances the ring. `SetFence` and `QueueCommands` positions come from it, and the midasm hooks publish those positions.
  - It patches the vertex shader in place. `gpu_draw.cpp` hashes the patched bytes, so this must not change what the renderer reads.
  - It performs command-buffer recording (`D3DDevice_BeginCommandBuffer` 0x822F9A88). That must keep the guest path because `gpu_cmdbuf.cpp` parses recorded buffers.
  - Risk: medium-high. Start with a cvar that skips the body outside `cmdbuf::Recording(device)` and clears the pending mask by hand.
- **Memoize `PatchVertexShaderToMatchVertexDeclaration` (sub_823038D8)** keyed by (shader microcode hash, declaration). The output is a pure function of its inputs. The renderer already does the same patch, so one shared cache removes both. Feasible, risk medium.
- **Shader constant uploads**. `SetVertexShaderConstantFN` / `SetPixelShaderConstantFN` (sub_822EAE80, sub_822EAF58) write the shadow the renderer reads. Keep them. Only the shadow-to-ring copy in `SetPending_AluConstants` (sub_82303788) is redundant. The `Gpu*ShaderConstantF4` ring loads (sub_822F6D18 hooked, sub_822F6DA8, sub_822F74F8) are the renderer's input and must stay.
- **Render state shadowing**. `SetRenderState_*`, `SetSamplerState_*`, `SetBlendState` and `SetTexture` maintain the shadow. Keep them. `SetPending_RenderStates` / `SetPending_FetchConstants` / `SetPending_HiZEnable` only serialize it. They can be stubbed together with the draw body.
- **FXL effects** (`FXLEffect_Commit` sub_82475000, R 52/73). This layer sits above the device. It feeds the shadow, so forwarding means reimplementing FXL. Not worth it now.
- **Vertex/index endian swaps and copies**. The guest does no per-frame swaps (`XGEndianSwap*` not seen). The per-draw copies are host side: `StreamSnapshotPool::Copy` R 207 and `PlaceIndices` R 293 incl. These are the largest single cost on the render thread but outside the scope of guest hooks.
- **Texture locking and tiling**. `LockSurface` / `Lock2DSurface` (sub_822DEAF8, sub_822DEBD0) are hooked. `XGUntile*` / `XGTile*` are not seen per frame. Nothing to forward.
- **Resolve / Clear** (sub_822E74D0, sub_822E5C58) are hooked and still run the guest body (R 10 + 26 incl, `ClearSurface` sub_822E5030 R 16 incl). The body emits EDRAM resolve packets only. Stubbing it after capture looks feasible. Risk: medium, because Resolve also updates the texture header base and the tracker's coverage.
- **GPU sync waits**. `BlockUntilIdle` (sub_822D9AB0), `BlockOnFence` (sub_822D8578), `IsFencePending` (sub_822D9850) and `IsBusy` (sub_822D97B8) are hooked. Fence and primary-index writebacks are midasm hooks. `KickOff` (sub_822D96B0, 122 callers) is not seen in the profile. None of these burn CPU now.
- **Present / Swap**. `D3DDevice_Swap` (sub_822F50C0) is hooked. Its 614 render-thread samples are the host `EndFrame` waiting on the two-frame queue, plus the optional `display::FrameLimit` sleep. `D3DDevice_Present` (sub_822F5720) is not hooked and not seen.

## sub_82324CE0 and other wait paths

`sub_82324CE0` is XAPI `WaitForMultipleObjectsEx(count, handles, waitAll, timeout, alertable)`. It copies the handle array, converts the timeout with sub_8232F1F0, and calls `NtWaitForMultipleObjectsEx`. It retries on `STATUS_ALERTED` (257) when alertable. It is a blocking kernel wait, not a spin loop. sub_82324E10 is the non-alertable wrapper (`li r7,0`).

- **Main thread (2771 samples, 69%)**: `sub_8212BA28` (thread loop) > `sub_82128328` (frame tick) > `sub_82210020` > `WaitForMultipleObjects(3, {obj+108, obj+12, arg}, WaitAny, timeout from 0x82991940)`. `obj+108` is the event the render thread procedure `sub_82212090` sets with `SetEvent` (sub_82324888) when it finishes with a frame. `sub_82210020` clears it on success (sub_82324A28) and returns 2 on timeout. The main thread is therefore waiting for the render thread to accept the next frame. This is the hand-off of a two-stage pipeline, not wasted CPU. Replacing the wait gains nothing. Making the render thread faster does.
- **Render thread (524 samples, 13%)**: `sub_82212090` > `sub_82121418` > `WaitForMultipleObjects(2, {obj+52, arg}, WaitAny, INFINITE)`, then `ResetEvent(obj+52)`. This is the render thread waiting for the main thread to post work. With both sides waiting part of the time, the pipeline is serialized by the host `EndFrame` wait (614) plus host renderer time (1522).
- **Threads 0x20 and 0x22**: wait in sub_82324CE0 under sub_8234E760 / sub_8234E860 (an XAPI/XAM worker started through `XapiThreadStartup`) for the whole profile. Idle.
- **Threads 7, 8, 9, A**: `RtlSleep` (sub_8232F508) loops in sub_822551C0, sub_8222C918 (via `SleepEx` sub_82324E18), sub_82246678 and sub_82249820. These are periodic workers (network, session, storage). They sleep and do not spin.
- **Threads 4, B, 0x12**: `WaitForSingleObjectEx` (sub_8232E338). Thread 0x12 is the voice engine (`XHVWorkerThreadProc`).
- **Threads 0x10, 0x11, 0x21**: audio/XMA workers waiting in sub_8239EF98. Thread 0x10 is busy about 9% (DSP ranks 39-41).
- **Spin locks**: no `db16cyc`/`db8cyc` hint loops were found. The only lock-like busy work on the hot threads is the global lock taken by the interlocked idiom (rank 1). It shows up as ntdll time under sub_82401EA8, sub_82401D58, sub_828B08E0 and sub_8211D400. `RtlEnterCriticalSection` is a host import. Its ntdll time under sub_82128A90 / sub_82128B50 (allocator lock) and sub_823637D8 (XMA lock) is the remaining lock cost.
